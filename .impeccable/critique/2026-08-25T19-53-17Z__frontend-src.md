## Overall Impression

The domain modeling is the real strength here — EPSS parsing, exposure scoring, provenance-tagged compliance evidence are specific and defensible to an auditor. The gut-punch is that the app's two most consequential moments — a scan silently failing, a vendor being deleted — get the least design attention in the whole product, while the screen a user sees exactly once (auth) got the most. That's backwards for a tool whose entire value proposition is "you can trust what this dashboard is telling you right now."

## What's Working

1. **`SignInMethodsModal`'s lockout guardrails** — disabled-button tooltips prevent removing your last sign-in method, explaining exactly why. Error prevention applied precisely where a mistake would be catastrophic.
2. **The "How is this calculated?" scoring explainer** (`VendorDetail.jsx:515-556`) — shows the actual multiplier table (PII ×1.4, Financial ×1.6, Critical Infra ×2.0). Turns an opaque number into something defensible, and it's specific to this product's job.
3. **Honest epistemic-limitation copy** throughout — "may be significantly lower than actual risk," "based on public evidence only, not a verified audit," EventFeed's passive-scanning caveat. Refusing to overclaim confidence is real trust-building for a security tool, not boilerplate.

## Priority Issues

**[P1] Scan and delete failures are invisible to the user**
*Why it matters*: `Dashboard.jsx` `handleDelete` has no try/catch — a failed delete throws an unhandled rejection with zero UI feedback. `handleScan` in both `Dashboard.jsx` and `VendorDetail.jsx` only `console.error`s on failure — the spinner stops and nothing else happens, so a vendor's risk data can go silently stale. In a risk-monitoring product, a scan that fails without telling anyone manufactures false assurance — the worst failure mode this app can have.
*Fix*: Surface a dismissible error banner/toast on every catch block that currently only logs to console.
*Suggested command*: `/impeccable harden`

**[P1] Risk-band thresholds are inconsistent across the app**
*Why it matters*: The "medium risk" cutoff is 35 in `VendorCard.jsx`, `GuestScanPage.jsx`, and `ScoreGauge.jsx`, but 40 in `Dashboard.jsx`, `VendorDetail.jsx`, and `ScoreChart.jsx`. A vendor scoring 37 shows as amber/"Medium" on its own card but gets counted into the "Low Risk" StatPill on the same screen. `RiskBadge.jsx` already exports a correct single-source `riskLevel(score)` helper — it's just not consistently imported.
*Fix*: Replace every duplicated inline threshold with `riskLevel()` from `RiskBadge.jsx`.
*Suggested command*: `/impeccable harden`

**[P1] Vendor deletion gets a bare `confirm()` while account deletion gets a hardened flow**
*Why it matters*: `Dashboard.jsx:99` uses `confirm('Remove this vendor?')` with no mention that scan history, risk events, and analyst notes are also destroyed — while `DeleteAccountModal.jsx` uses two-step typed confirmation plus step-up auth for a comparably (arguably less) consequential action on the user's own account.
*Fix*: Reuse the existing modal pattern with an itemized consequence list, matching the seriousness already given to account deletion.
*Suggested command*: `/impeccable harden`

**[P2] VendorDetail exceeds the ≤4-choice cognitive-load guideline twice on one page**
*Why it matters*: Data Sensitivity renders 7 selectable options and Review Schedule renders 6, both as fully expanded button grids in the same continuous scroll as score, scoring-model explainer, compliance grid, events, and notes — no sequencing, no collapse, nothing deferred.
*Fix*: Convert both to labeled dropdowns (keeps at-a-glance current value) or split VendorDetail into tabs (Overview / Compliance / Events / Notes) so configuration doesn't compete with score/events on first load.
*Suggested command*: `/impeccable layout`

**[P2] Key tooltips are hover-only with no keyboard/focus equivalent**
*Why it matters*: The "How is this calculated?" scoring explainer (`VendorDetail.jsx:515-529`, `.group-hover:block`) and the accepted-risk justification tooltip (`EventFeed.jsx:102-103`, `onMouseEnter`/`onMouseLeave` only) are unreachable by keyboard or screen reader — and the scoring explainer is arguably the app's single most important piece of contextual help. Selector button grids also lack `radiogroup`/`aria-pressed` semantics, so a screen reader announces plain buttons instead of "1 of 7 selected."
*Fix*: Add `focus-within`/`onFocus`/`onBlur` fallbacks alongside the hover handlers; add proper ARIA roles to the selector grids.
*Suggested command*: `/impeccable audit`

## Persona Red Flags

**Alex (Power User, manages many vendors)**: Hits a hard, self-acknowledged product ceiling — `Scan All`'s own tooltip admits "Works best with 1-2 vendors on the free tier... Scanning 3+ can time out," with no async job queue, no per-vendor progress, no completion notification. No bulk select/rescan/delete. The High/Medium/Low StatPills look clickable but aren't. CSV export is the only real efficiency win in the app.

**Sam (Accessibility)**: Can't reach the scoring explainer or the accepted-risk justification tooltip by keyboard at all (see P2 above). Sensitivity/Review-interval button grids read as plain unlabeled buttons to a screen reader, not as a selected-state group.

**Jordan (First-Timer)**: After adding a vendor, nothing on the resulting card distinguishes "scan this next" from the Delete button sitting right beside it. Landing on a never-scanned vendor's detail page immediately surfaces all 7 configuration/info panels before Jordan has seen a single real result — the "aha" moment is buried under administrivia. The recurring footer line "New accounts: Google, then a passkey" signals an unusual auth model but never explains what a passkey is inline.

## Minor Observations

- `ScoreGauge.jsx` appears unused by any reviewed page (VendorDetail builds its own score display) — worth a dead-component check.
- Footer's GitHub link points to a personal-looking username, publicly exposed in the footer of an internal tool.
- Heavy reliance on inline `style={{...}}` with raw hex duplicated across nearly every file instead of the `--accent`/`--accent-h` tokens already defined in `index.css` — no shared Button/Input/Modal primitives, which is exactly how the risk-threshold bug above happened.
- `--risk-crit` and `--risk-high` are defined as the literal same hex value (`#F04438`) — the "Critical" distinction exists in name only.
- No `prefers-reduced-motion` handling anywhere, despite continuous 44-92s orb drift, pulse rings, and trace-draw animations on every page. Detector-corroborated (bounce-easing ×2, dot-grid decoration).

## Questions to Consider

- Is the consumer-SaaS "radar pulse / drifting nebula" auth aesthetic the right register for security officers logging in daily, or would the dashboard's calmer, already-sober tone serve better on the 100th login than the 1st?
- The scoring model and EPSS language are genuinely sophisticated — has anyone checked whether a first-time, non-technical user can explain what a card's number means, or does that sophistication mostly serve power users while quietly overwhelming everyone else?
- Vendor deletion (losing an audit trail) gets a bare `confirm()` while account deletion gets a hardened flow — was that prioritization deliberate, or does it just reflect which screen got built last?
